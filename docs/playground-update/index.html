Aggiornare i playground

Nota personale, non linkata: cosa fare quando cambio Kairos o Mnemo.

In breve Requisiti Cosa viene copiato Esempi Test Problemi

Le pagine /docs/kairos/ e /docs/mnemo/ eseguono i programmi nel browser con una copia dei due progetti. Quando modifico ../kairos o ../mnemo, il sito non si aggiorna da solo: bisogna rigenerare la copia e fare commit.

In breve

cd ~/Desktop/nicologiuliani6.github.io
tools/update-playgrounds.sh            # ricompila la VM e copia Kairos + Mnemo
python3 -m http.server 8000            # poi apri le due pagine e premi Run
git add docs/kairos/play docs/mnemo/play
git commit -m "playgrounds: update to kairos <hash>, mnemo <hash>"
git push

Lo script stampa l'hash dei commit da cui ha copiato i file: lo metto nel messaggio di commit. Se un repo ha modifiche non committate, lo script avvisa e le copia lo stesso.

Nel dubbio: tools/update-playgrounds.sh, che fa tutto.

Requisiti

  • Emscripten in ~/emsdk, per compilare la VM in WebAssembly. Lo script lo attiva da solo. Per reinstallarlo: git clone https://github.com/emscripten-core/emsdk.git ~/emsdk && cd ~/emsdk && ./emsdk install latest && ./emsdk activate latest
  • Il venv di Kairos (../kairos/venv, da make install-deps): da lì vengono PLY e il pip che scarica pcpp.
  • I due repo clonati accanto al sito: ~/Desktop/kairos e ~/Desktop/mnemo. Altrimenti si passano i percorsi: tools/update-playgrounds.sh /path/kairos /path/mnemo.

Ogni cartella py/ ha un files.txt con l'elenco dei file da caricare in Pyodide; lo rigenerano gli script. Se aggiungo un modulo Python a Kairos o a Mnemo viene preso in automatico, purché stia nelle cartelle sopra.

Scritti a mano, non generati (gli script non li toccano):

  • docs/kairos/play/playground.js e playground.css: l'interfaccia, condivisa dalle due pagine;
  • docs/kairos/play/compile-worker.js: Pyodide → bytecode Kairos;
  • docs/mnemo/play/compile-worker.js: Pyodide → Mnemo → bytecode, con il ponte pcpp;
  • docs/kairos/play/vm-worker.js: esegue il bytecode sulla VM (lo script lo copia anche in docs/mnemo/play/).

Devo toccarli solo se cambia l'interfaccia tra i pezzi: la funzione C vm_run_from_string, le funzioni Python usate dai compile worker (parser.parse, desugar_try, run_static_checks, ByteCode_Compiler, compile_c_to_kairos, mnemo.c_parse.preprocess_file) o il formato del bytecode in coda.

Test prima del push

  1. python3 -m http.server 8000 dalla radice del sito.
  2. Apro http://localhost:8000/docs/kairos/ e /docs/mnemo/. Alla prima visita la pagina si ricarica da sola: è il service worker.
  3. Premo Run su ogni scheda e confronto con kairos file.kairos e mnemo file.c nel terminale.
  4. Provo anche Firefox: è più severo di Chrome sugli header (vedi sotto).
  5. Se vedo ancora la versione vecchia: Ctrl+Shift+R.
  6. Dopo il push riprovo le pagine online: in locale i file con _ iniziale ci sono sempre, online no (vedi sotto).

Problemi già incontrati

SintomoCausa e rimedio
Online (non in locale): SyntaxError su CSS in __init__.py, oppure "could not load … (HTTP 404)" GitHub Pages usa Jekyll, che non pubblica i file il cui nome inizia con _. Vanno elencati in include in _config.yml (ci sono __init__.py e __main__.py). Per controllare dopo una rebuild: find docs -name '_*'.
"VM error: worker failed" solo su Firefox Uno script di worker caricato da fuori la cartella della pagina non riceve gli header COOP/COEP del service worker. Ogni pagina deve avere la sua copia di vm-worker.js e della VM nella propria cartella (per Mnemo lo fa lo script).
"this page is not cross-origin isolated" Il service worker coi-serviceworker.js non è attivo: ricaricare. Nelle finestre private può essere bloccato. Ogni pagina con playground deve includerlo come primo script nell'<head>.
Il playground resta su "running…" anche per programmi senza par I thread della VM partono dall'URL di vm-worker.js, che deve caricare kairos-vm.js e non registrare onmessage quando self.name === 'em-pthread'.
Errori di compilazione C con il numero di riga sbagliato Il ponte pcpp antepone gli #include forzati: serve la riga #line 1 dopo di loro (già nel compile worker di Mnemo).
Output diverso da mnemo nativo Controllare che pcpp dia lo stesso preprocessing di gcc -E: confrontare compile_c_to_kairos con i due preprocessori su tests/c/examples/*.c (l'ultima volta 55 su 55 identici).
Warning shift count >= width of type compilando la VM In WebAssembly i puntatori sono a 32 bit: p >> 32 su un uintptr_t va fatto passando per uint64_t (vedi vm_ops.h, codifica dei canali).
Il labirinto di Mnemo impiega ~30 s su Firefox Firefox è più lento di Chrome su questa VM WebAssembly (Chrome ~4 s, nativo ~3 s). Non è un blocco; il limite di Mnemo è 60 s (timeoutMs in index.html).

Versioni fissate

  • Pyodide v0.27.2 dalla CDN jsDelivr, nei due compile-worker.js. Mnemo usa il pycparser incluso in Pyodide.
  • pcpp==1.30 in build-mnemo-playground.sh.
  • coi-serviceworker 0.1.7, copiato in docs/kairos/ e docs/mnemo/.
